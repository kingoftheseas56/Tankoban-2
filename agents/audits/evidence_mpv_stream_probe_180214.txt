## 3. Stall behavior

**NOT INDUCED THIS SMOKE.** No natural stall occurred in the 5-min window because the Torrentio magnet had a healthy seed pool + the first source was 1080p H.265 (compact bitrate) so the stream-server stayed >5 minutes ahead of playback throughout. No network-cut test was performed (Hemanth-driven decision to ship this as a partial probe).

**Implications of the absence:**
- `paused-for-cache`: **0 events fired** in the entire 5-min steady-state window. Confirms it's an EDGE-DRIVEN signal — fires only on the boolean transition false↔true. Useful for `bufferingStarted`/`bufferingEnded` translation in 1.C exactly because it's edge-driven (no spurious spam).
- `cache-buffering-state`: **0 events fired**. Same edge-driven semantics; only changes during initial buffer-fill or when buffer state crosses a threshold.

This itself is informative for 1.C/1.E shape:
- Don't try to use `cache-buffering-state` as a real-time progress indicator. It's not chatty enough.
- Use `paused-for-cache` for the bufferingStarted/Ended edge.
- Use `demuxer-cache-state.cache-duration` for the "how full is the buffer" continuous signal — it's the chatty property and has actual second-resolution depth.

**A targeted stall test before 1.E ships would be useful** (seek past cache-end, observe the paused-for-cache transition + recovery). Flagging this as a follow-up sub-probe inside 1.E execution rather than re-firing 1.B.

## 6. Implications for 1.C / 1.E shape

**1.C cache property observation — concrete recommendation:**
- Wire `paused-for-cache` (FLAG) → `bufferingStarted` on rising edge, `bufferingEnded` on falling edge. Edge-driven semantics map cleanly to the IPlayerBackend signal pair.
- Do NOT wire `cache-buffering-state` (DOUBLE) as a `cacheStateChanged` source — it's not chatty enough for real-time progress, and the LoadingOverlay::setCacheProgress signature wants 4 fields (bytesAhead, inputRateBps, etaResumeSec, cacheDurationSec) that mpv doesn't atomically provide via this property.
- DO wire `demuxer-cache-state` (NODE) as the `cacheStateChanged` source. Synthesize the 4 LoadingOverlay fields from the node payload:
  - `bytesAhead` ← `payload.fw-bytes`
  - `inputRateBps` ← `payload.raw-input-rate`
  - `etaResumeSec` ← compute from `cache-duration` and `raw-input-rate`, OR pass -1.0 (unmeasurable) if we don't need ETA
  - `cacheDurationSec` ← `payload.cache-duration`
- Open question for 1.C: throttle the demuxer-cache-state emission to ~2 Hz (matching ffmpeg sidecar's cache_state cadence per `native_sidecar/src/main.cpp:752-780`)? mpv fires it sub-second; uncapped re-emit would over-flood LoadingOverlay's UI thread. Suggest a 500ms throttle in the MpvBackend handler.

**1.E transparent stall semantics — concrete recommendation:**
- Plan-mode design (m_inStallPause flag + suppress stateChanged emit while flag is true) is correct.
- Need a small additional smoke INSIDE 1.E execution: induce a stall (seek past cache-end), confirm `paused-for-cache=true` fires, confirm mpv's `pause` property also fires true at the same time, verify the m_inStallPause gate correctly suppresses stateChanged while letting bufferingStarted through. Allocate ~10 min of 1.E scope to this.
- Sequencing: 1.C ships first (paused-for-cache → bufferingStarted/Ended translation). 1.E ships after, gating the pause-property-driven stateChanged emit on m_inStallPause flag.

## 7. Anomalies / unexpected findings

- **`cache-secs` silent throughout the smoke.** Possibly not a documented observable in libmpv 0.41.0 at the property name "cache-secs", OR the value didn't change enough to fire a property event. The same data is in `demuxer-cache-state.cache-duration`. Recommend dropping cache-secs from 1.C wiring.
- **HUD reveal failed via `L` keypress.** Sent via windows-mcp Shortcut after focus call; HUD did not appear. May be a focus-routing issue specific to the mpv-rendering case (MpvVideoWidget consumes keys differently than FrameCanvas?). Quick follow-up sanity check after 1.B: smoke HUD reveal on mpv backend specifically, confirm transport bar / seek slider / time labels all behave equivalently to ffmpeg backend. NOT a 1.B-blocker; flagged for 1.D verify (the parent plan's "verify-only" sub-phase).
- **Player closed mid-smoke at ~18:08pm.** Cause uncertain — possibly the `L` keypress hit a different binding when focus was wrong, or a click into/near the canvas registered as something else. Doesn't invalidate the data captured pre-close.
- **stremio-runtime.exe was already running at smoke start.** It survives across player open/close — good. Process lifecycle is owned by Tankoban session, not per-stream.
- **`demuxer-cache-state` payload fields beyond what mpv docs explicitly call out:** `bof-cached`, `eof-c…(truncated)`, `debug-low-level-seeks`, `debug-byte-level-seeks`, `debug-ts-last`. Useful for 1.C diagnostics but not load-bearing for the IPlayerBackend signal translation.
