# TTS Perf Audit — 2026-05-06

By Agent 7 (Codex). For Agent 2 (Book Reader), with Agent 0 expected to author the downstream fix-TODO after Agent 2 validates.

Scope: read-only Trigger C audit of the current Tankoban Book Reader TTS pipeline for speed, responsiveness, and seamlessness. No `src/` or `resources/` code was modified. No live benchmarking was run; every latency number below is either already in code comments, sourced externally, or explicitly marked as a measurement gap. Stremio TTS is out of scope because Stremio has no comparable TTS surface.

Reference comparison: Microsoft Edge Read Aloud, Speechify, Piper, Voice Dream Reader, Foliate, the public Edge-TTS protocol ecosystem, and the prior Agent 7 Edge TTS audit / closed `EDGE_TTS_FIX_TODO`.

## A. Current architecture

### Observed flow

```text
User clicks Listen
  -> tts_hud.js toggles window.booksTTS.play/pause/resume
  -> tts_core.js initializes Foliate TTS and builds a block queue
  -> tts_core.js selects the single supported Edge engine after probe
  -> tts_engine_edge.js checks local JS LRU, then attempts streaming
  -> streaming gate fails today because window.__ttsEdgeStream is absent
  -> tts_engine_edge.js calls Tanko.api.booksTtsEdge.synth(...)
  -> BookReader.cpp injected QWebChannel shim assigns a request id
  -> BookBridge.cpp invokes EdgeTtsWorker::synth on EdgeTtsThread
  -> EdgeTtsWorker calls EdgeTtsClient::synth synchronously on worker thread
  -> EdgeTtsClient reuses an open QWebSocket if still connected, otherwise handshakes
  -> EdgeTtsClient sends speech.config and one SSML text frame
  -> EdgeTtsClient accumulates all MP3 binary frames and WordBoundary metadata
  -> EdgeTtsClient returns full MP3 bytes + boundaries to the UI bridge
  -> BookBridge base64-encodes the full MP3 into a QJsonObject
  -> tts_engine_edge.js decodes base64 into a Blob and plays HTMLAudioElement
  -> tts_core.js advances to the next Foliate queue block on audio ended
  -> JS preloads ahead/behind, and prepareNext tries to prebuffer the next Audio
```

| Foliate queue generation | `tts_core.js` calls `view.initTTS('word', highlightRange)` and walks blocks with `foliate.tts.start()` / `next()` to fill `_queue.items` (`tts_core.js:758-778`, `720-749`). | Potential first-click cost before any audio request, especially on large chapters. No instrumentation found for queue-build duration. |

Warmup is fire-and-forget and uses a second probe (`EdgeTtsWorker.cpp:56-63`). |

It works only if foreground synth does not monopolize the single worker and preloads finish before the block ends. |

### Queue and buffer ownership

- JS cache: per-engine-instance `Map` capped at 50 entries, key `voice|rate|pitch|text`, stores Blob/audioUrl and boundaries (`tts_engine_edge.js:59-67`, `78-90`).
- C++ cache: per-`EdgeTtsClient` strict LRU capped at 200 entries, key SHA1 over text, voice, rate, pitch, and format (`EdgeTtsClient.h:132-155`, `EdgeTtsClient.cpp:605-646`).
- Network queue: one `EdgeTtsWorker` object on one `QThread`; all synth and preload calls entering native side are serialized by that worker (`EdgeTtsWorker.cpp:34-40`).
- Audio queue: one active `HTMLAudioElement`; optional `_prepAudio` for next-block prebuffering; no explicit PCM ring buffer or crossfade pipeline found (`tts_engine_edge.js:97-162`, `261-271`).

### Hypotheses for Agent 2 to validate

- **Hypothesis -** The largest first-audio-byte cost on cache miss is not UI blocking; it is the combination of full-block native synthesis plus base64 return plus Blob decode before `audio.play()`. **Agent 2 to validate.**
- **Hypothesis -** Single-worker serialization means aggressive lookahead can compete with the foreground utterance and may sometimes delay rather than improve the next audible block. **Agent 2 to validate.**
- **Hypothesis -** The existing 50-entry JS cache and 200-entry C++ cache duplicate memory without a single owner for persistence, eviction telemetry, or hit-rate reporting. **Agent 2 to validate.**

## B. Flaws and inefficiencies

### Observations

1. **Cold start has only opportunistic reuse.** `ensureSocketOpen()` reuses a connected socket, but if the socket is closed it destroys and reconnects with a 5s connect timeout (`EdgeTtsClient.cpp:377-435`, `438-444`). There is no pool, ping, idle expiry policy, or startup health metric.

2. **Warmup is another probe, not a persistent prepared synth channel.** `EdgeTtsWorker::warmup()` synthesizes `"Edge probe."` with `en-US-AndrewNeural` (`EdgeTtsWorker.cpp:56-63`). It may warm the socket and DNS/TLS path, but it does not pre-synthesize the user-visible first block.

3. **Foreground fallback waits for complete audio.** `runRoundTrip()` appends MP3 chunks and exits on `turn.end`; `synth()` rejects missing `turn.end` as `incomplete_synth` (`EdgeTtsClient.cpp:231-250`, `277-372`). JS starts playback only after receiving `audioBase64`/Blob (`tts_engine_edge.js:1069-1104`).

4. **Native streaming is still pending.** The JS path attempts `_speakStream()` first (`tts_engine_edge.js:1041-1052`), but stream support requires `window.__ttsEdgeStream` (`tts_engine_edge.js:700-706`) and `EdgeTtsWorker::synthStream()` currently emits `phase_4_pending` (`EdgeTtsWorker.cpp:42-48`). This matches the closed TODO's Phase 4 deferral gate (`agents/_archive/todos/EDGE_TTS_FIX_TODO.md:291-339`).

5. **The streaming scaffold is old-Python-shaped in comments and wire expectations.** `tts_engine_edge.js` still says audio chunks arrive from Python (`tts_engine_edge.js:695-697`), while current native code is Qt direct WSS. This is documentation drift, but it also flags that the JS stream event bridge was never reconciled with the C++ implementation.

6. **Two cache layers are memory-only.** C++ LRU is 200 entries and disappears when the `EdgeTtsClient` is destroyed (`EdgeTtsClient.h:153-155`); JS LRU is 50 entries inside one engine instance (`tts_engine_edge.js:59-63`). Neither survives app restart.

7. **Cache key shape mostly matches the perf goal.** C++ includes text + voice + rate + pitch + output format (`EdgeTtsClient.cpp:605-616`). JS includes text + voice + rate + pitch (`tts_engine_edge.js:65-67`) but not output format; format is effectively fixed to MP3 today.

8. **Voice table is static and likely stale.** Current code pins an Edge version of `1-130.0.2849.68` and only 23 English voices (`EdgeTtsClient.cpp:35-47`, `116-154`). Current public `rany2/edge-tts` constants use Chromium `143.0.3650.75`, expose a voice-list endpoint, and default to `en-US-EmmaMultilingualNeural` (`rany2 constants.py:335-348`). Static voices are fast, but drift risk is real.

9. **Error recovery resets after repeated JS diagnostics, not per failure class.** JS increments `_synthErrorCount` for codes containing `fail` or `timeout`, and calls `resetInstance()` after two such diagnostics (`tts_engine_edge.js:229-247`). C++ returns structured reasons including `wss_handshake_fail`, `network_blocked`, `no_audio_received`, and `incomplete_synth` (`EdgeTtsClient.cpp:233-244`, `283-294`). There is no backoff/circuit-breaker table per reason.

10. **Pause is true HTMLAudio pause, but core resume restarts.** Engine pause calls `audio.pause()` and keeps boundary state (`tts_engine_edge.js:1220-1225`), but `tts_core.resume()` cancels all engines and restarts the current segment from a resume point (`tts_core.js:1331-1340`). The fallback path does not simply call `engine.resume()` for the same audio.

11. **Scrub/seek is block-index oriented.** Segment seek and approximate time jumps cancel current audio, pick a new queue item, and start/restart synthesis (`tts_core.js:1423-1469`, `1484-1524`). There is no instant intra-audio scrub except the resume hint path when boundaries exist (`tts_engine_edge.js:540-570`).

12. **Voice/rate changes are intentionally throttled and restart playback.** Core uses a 1500ms reconfig throttle (`tts_core.js:560-561`, `1764-1792`). During active playback it captures a resume point, cancels, applies the selection, and restarts (`tts_core.js:1724-1760`). This is stable, but it does not meet a strict `<100ms` responsiveness goal.

13. **Highlight sync is ambitious but timer-based.** Word boundaries are mapped through normalized text and polled against `audio.currentTime` (`tts_engine_edge.js:449-562`, `389-445`). The poll cadence is reasonable, but DOM paint timing can still jitter, and incorrect word matching can drift on repeated/punctuated text.

14. **There is no click/pop suppression layer.** Playback swaps `src` between Blob/object URLs and can replace the active Audio element with `_prepAudio` (`tts_engine_edge.js:573-680`, `1115-1140`). No crossfade, zero-crossing alignment, decode preroll envelope, or PCM-level edge treatment was found.

15. **UI feedback exists, but first-click instrumentation is thin.** JS exposes progress messages such as `Initializing...`, `Probing engine...`, `Warming up...`, and `Ready` (`tts_core.js:1160-1233`) and buffering state (`tts_engine_edge.js:1038-1042`, `1110-1112`), but no end-to-end `listen_click_to_first_audio_ms` metric was found.

16. **Phase 4 gate has not been re-opened with measurements.** The old gate said to defer streaming if sentence-batch latency was acceptable under 1.5s, and pursue if first sentence latency exceeded 3s (`agents/_archive/todos/EDGE_TTS_FIX_TODO.md:327-339`). Current request changes the target to `<500ms perceived`, which is materially stricter than the old gate.

### Hypotheses for Agent 2 to validate

- **Hypothesis -** The old Phase 4 deferral gate is obsolete under Hemanth's new `<500ms perceived` target; even "acceptable" 1-2s sentence-batch playback now deviates from the requested speed bar. **Agent 2 to validate.**
- **Hypothesis -** True pause/resume can hit `<100ms` if `tts_core.resume()` uses `engine.resume()` for the normal PAUSED state instead of always canceling and restarting. **Agent 2 to validate.**
- **Hypothesis -** The 1500ms rate/voice coalescing window is product-safe for avoiding glitches, but it directly conflicts with the named responsiveness target. **Agent 2 to validate.**
- **Hypothesis -** C++ socket reuse exists, but without foreground synth prioritization and stream chunk delivery it cannot make first audio feel instantaneous on a cache miss. **Agent 2 to validate.**
- **Hypothesis -** Current word-level highlight is likely good enough for short blocks but should be measured against long paragraphs, punctuation-heavy prose, and high playback rates before being treated as "seamless." **Agent 2 to validate.**

## C. Industry comparisons

### C.1 Edge browser Read Aloud

Microsoft's public Edge docs establish the user-facing standard: Read Aloud is available from page context menus, toolbar paths, PDFs, and Immersive Reader, and Ctrl+Shift+U starts/stops it (`ReadAloudEnabled` policy lines 41-44; Microsoft Support lines 214-226). The Edge learning page says the toolbar exposes Play/Pause, Forward/Backward, speed, and voice options, and that online use unlocks dozens of natural voices (Microsoft Edge learning center lines 118-126).

The internal Edge implementation is not documented publicly. The closest verifiable implementation surface is the public Edge-TTS protocol ecosystem. `rany2/edge-tts` uses the same `speech.platform.bing.com/consumer/speech/synthesize/readaloud/edge/v1` WSS URL, trusted token, Edge-like Origin, and Sec-MS-GEC versioning (`rany2 constants.py:335-375`). It streams audio chunks and metadata and raises `NoAudioReceived` when the service produces no audio (`rany2 communicate.py:2434-2455`). A 2026 Microsoft Q&A answer also distinguishes local voices from online voices and states that online voice audio is streamed back, while local voices avoid network latency (Microsoft Q&A lines 111-137). Treat that Q&A as support context, not an official architecture guarantee.

Applicability: Tankoban already mirrors the direct Edge-WSS path. The main deviation is not endpoint choice; it is that Edge browser has a fully integrated product loop around streaming, online/offline voice fallback, toolbar responsiveness, and voice-speed controls, while Tankoban currently has full-block MP3 fallback and a disabled native streaming bridge.

### C.2 Speechify

Speechify's public API docs describe the pattern Hemanth is asking for: a streaming endpoint delivers audio chunks as generated so playback can begin before the full audio is ready; the docs explicitly compare "after full generation" with "immediately" for stream playback, and list PCM as the lowest-latency format. The same docs call out long-form content and low-latency apps as the target use case, and warn that mid-stream failures require byte-count and remaining-text retry logic.

Speechify's SIMBA 3.0 blog claims production voice workloads with low-latency streaming audio, real-time output formats, speech marks for word-level timing, and sub-250ms latency for voice assistant timing (Speechify SIMBA lines 300-338). Its real-time TTS article emphasizes latency budgets, WebRTC streaming, and edge caching, with a stated sub-200ms performance target for interactive systems (Speechify real-time blog lines 274-300). These are vendor claims, but they are directionally consistent with the architecture: stream audio early, keep formats latency-friendly, own speech marks, and use edge/caching infrastructure.

Applicability: Tankoban does not need Speechify's global platform, but the relevant design standard is clear: make the first playable chunk an output of the synth pipeline, not the end of it; keep retry/resume segmented; and expose marks as synchronization data rather than post-hoc polling only.

### C.3 Piper

Piper is a fast local neural TTS engine. The original `rhasspy/piper` repo now points development to `OHF-Voice/piper1-gpl`; the current Open Home Foundation repo describes Piper as a fast local neural text-to-speech engine embedding `espeak-ng` for phonemization, with C/C++ API and web-server options (OHF Piper lines 310-323). Piper's C++ code loads ONNX model sessions and synthesizes phoneme ids into audio buffers, tracking inference seconds, audio seconds, and real-time factor (`piper.cpp:2033-2147` from the archived repo).

Piper's main performance advantage is no network path: no WSS handshake, no cloud routing, no online-voice stalls. Its tradeoff is product quality and packaging: voice models must be shipped or downloaded, GPL status in the current maintained repo needs legal review, phonemization and model loading must be integrated, and naturalness may not match Edge online neural voices for long prose.

Applicability: Piper is best framed as a fallback or optional "instant local" mode, not a replacement for Edge under current project memory. It could satisfy first-byte and offline reliability, but the project memory says Kokoro was removed and Edge TTS is the only acceptable engine unless Hemanth explicitly approves a new backend. Any Piper lift therefore needs Hemanth product/legal ratification first.

### C.4 Voice Dream Reader

Voice Dream Reader is a TTS-first reader, and its public help emphasizes music-player-like controls, a speech cursor whose location is remembered, voice/rate selection per content item, pronunciation dictionaries, and background audio behavior on iOS (Voice Dream help lines 197-227). Its feature list explicitly names on-the-fly speed and voice changes, per-book/article voice and rate memory, synchronized word and line highlighting, and continuous playlists (Voice Dream feature list lines 76-101).

No public low-level engine architecture was found. The observable standard is product behavior: TTS is not an add-on button; it is a persistent reader state with resume location, content-specific preferences, playlist continuity, and highlighting treated as primary reading affordances.

Applicability: Tankoban already has much of the HUD surface and progress persistence. It deviates in responsiveness because several controls cancel/restart synthesis rather than retime current audio, and in seamlessness because the audio path lacks a low-level continuous buffer/crossfade layer.

### C.5 Foliate

Tankoban already vendors Foliate-style TTS machinery. The local vendored `resources/book_reader/vendor/foliate/tts.js` builds SSML fragments with marks, tracks mark-to-range maps, supports start/resume/next/prev/from-range, and highlights the current range (`vendor/foliate/tts.js:205-280`). Foliate's maintainer discussion says Foliate supports TTS with speech-dispatcher and a navbar narration button (GitHub discussion #1200 lines 232-246).

Foliate's model is structurally simpler: it lets the platform speech service own playback while Foliate owns text ranges, marks, and navigation. That favors responsiveness because OS TTS engines usually expose pause/resume/rate/voice primitives directly, but it gives up deterministic Edge online neural voice quality and exact cloud speech-mark metadata.

Applicability: Tankoban should keep the Foliate text/range layer but avoid overloading it with audio-buffer responsibilities. The useful Foliate lesson is separation: document traversal and highlight ranges should be deterministic locally; audio generation should expose a small real-time contract of play, pause, resume, seek-to-mark, chunk, and mark events.

### Lift notes and validation questions

- L1 should not be treated as "missing"; socket reuse exists. The likely gap is lifecycle policy: keepalive, stale-socket detection, warm connection per voice, and foreground-priority scheduling.
- L2 is the biggest speed lift because it changes first audio from "after turn.end" to "after first appendable MP3 chunk." It is also the riskiest because MediaSource MP3 support and stream-event ordering must be proven in QtWebEngine.
- L3 already exists conceptually, but because native synth is a single serialized worker call, Agent 2 should validate whether preloads can starve foreground synth. A foreground queue plus low-priority lookahead queue may matter more than increasing lookahead count.
- L4 should be framed as a product/strategic option, not a default recommendation, because project memory explicitly forbids reintroducing non-Edge TTS without approval.
- L7 is the highest impact/effort candidate for the responsiveness target. It is small enough to ship early if Agent 2 confirms the current resume restart is not required for correctness.
- L9 is valuable for restarts and re-reading, but disk cache will not help first-time paragraphs. It should follow measurement and cache-key finalization.
