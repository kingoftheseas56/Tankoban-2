# Tankoban 2 Claude Code Audit

## Executive summary

Your setup is already doing several smart things that line up with the public Claude Code playbook: you use specialized agents, you've built a high-signal local control surface (`tankoctl` / `TankobanDevControl`) instead of forcing everything through GUI automation, and you've started introducing resource-lane rules where the real pain is shared mutable state. The biggest gap is that a lot of your current coordination is still socially enforced through large shared text files, while your actual failures are mechanical: startup latency, lock contention, shared build-state corruption, and token burn during wait states. Anthropic's latest guidance is pretty consistent on the underlying theme: keep always-loaded context small, use worktrees and isolated contexts for parallel work, prefer high-signal tools over broad ones, and push verbose or noisy work into subagents, hooks, or external tooling so the main conversation stays clean.

Two of your suspected causes are credible, but one important third cause stands out from the docs and is easy to miss: synchronous hooks. Claude Code's hook system can block prompt processing, and `UserPromptSubmit` hooks in particular use a much shorter default timeout for command/http/MCP-tool handlers, which is right in the same range as your "30–45 second before the spinner even appears" symptom. Session-start hooks are also explicitly supposed to stay fast. So before you assume MCP is the only villain, you should profile `congress-check.sh` and any other synchronous hook on the critical path.

On MCP specifically, there is no documented "keep a local stdio MCP warm across Claude Code sessions" feature. The public patterns instead point toward either using a stable installed binary instead of `uvx`/`npx` wrappers for hot-path servers, or running a persistent local server over Streamable HTTP and connecting to that. MCP itself is designed around long-lived stateful connections, so repeated cold-starts are a bad fit for the protocol's center of gravity; that makes your instinct about startup overhead directionally right even if it is not the only thing happening.

Your highest-impact structural change is to stop treating the flat repo plus shared `out/` as the default for concurrent editing and building. Anthropic's own docs point to worktrees as the built-in isolation pattern for parallel sessions, and Claude Code now exposes worktree-specific settings for branch base, sparse checkout, symlinked directories, and background isolation. In your environment, build-lane locking is still useful, but it should become a fallback for the rare flat-tree case, not the main defense against concurrent Ninja/MSVC clobbering.

On context and memory, the key public rule is brutally simple: `CLAUDE.md` is loaded in full every session, auto memory only loads the first 200 lines or 25KB of `MEMORY.md`, and imports help organization but not token usage. That means your present instinct is correct: if the brotherhood's structural knowledge keeps growing, the answer is not more imports; it is more aggressive relocation of procedures and role-specific instructions into skills, path-scoped rules, and topic memory files that are read only on demand.

On multi-agent design, the public evidence is more cautious than the general hype. Anthropic's own research says multi-agent systems shine when tasks are breadth-first and independently parallelizable, while coding tasks often have tighter dependencies; a recent failure-mode paper similarly finds that specification failure, inter-agent misalignment, and verification/termination issues remain dominant. In other words, your "brotherhood" is not wrong, but it needs harder interfaces, smaller task scopes, and fewer wait states if it is going to stay efficient.

## Findings for MCP performance, context, and coordination

### A. MCP server lifecycle and performance

**Direct answer.** The canonical fast path on Windows is still local stdio for tools that truly need machine access, because MCP's architecture describes stdio as direct local process communication with "optimal performance with no network overhead." But MCP is also explicitly stateful and built around long-lived connections, which means repeatedly launching wrapper commands that may need package-resolution logic is conceptually the opposite of what the protocol wants. Claude Code does not publicly document a stdio "daemon mode" that survives across sessions. The practical pre-warm pattern available in public docs is to run a persistent service and connect over Streamable HTTP, or at minimum to replace `uvx` / `npx` launchers with stable installed binaries or venv/tool installs so startup is just process exec, not environment re-materialization. Astral's own docs say `uvx` uses cached disposable environments but recommend `uv tool install` for tools used often; npm's docs say `npx` executes from local binaries or a central cache and installs what it needs if missing.

Your `.mcp.json` antipatterns to check are straightforward. First, avoid `alwaysLoad: true` on anything that is not genuinely required on every turn, because that forces startup blocking even though MCP startup is otherwise non-blocking by default. Second, keep tool deferral enabled; Claude Code now defers MCP tools and discovers them on demand via tool search, precisely to reduce up-front context and startup burden. Third, if a server is auxiliary rather than core, treat it as fail-soft: Claude Code already retries transient HTTP/SSE startup failures and then marks the server failed rather than collapsing the whole session, which is the right model for optional automation lanes. For your setup, `pywinauto-mcp` should clearly be auxiliary because your `TankobanDevControl` bridge is already the faster, more deterministic path for most in-app control.

One thing I would not over-attribute to MCP is the "nothing happens for 30–45 seconds before the spinner appears" symptom. Public Windows issue reports show that both subprocess startup timeouts and first-prompt hangs can happen in Claude Code's VS Code integration itself, sometimes extension-only, sometimes in other surfaces too. More importantly for *your* exact setup, synchronous `UserPromptSubmit` hooks can block prompt processing, and those command/http/MCP-tool hooks use a shorter default timeout on that event. Since you have `congress-check.sh` on `UserPromptSubmit`, that is a high-probability suspect that deserves measurement before further MCP tuning.

**Specific recommendation for Tankoban 2.** Replace every hot-path `uvx`/`npx` MCP server with a persistent install target first, not a wrapper. In practice that means pointing `.mcp.json` at a fixed executable, a fixed venv script, or a locally packaged tool path. If `pywinauto-mcp` remains important, consider running it as a persistent local Streamable HTTP service and registering it as an `http`/`streamable-http` MCP server so new Claude sessions connect to an already-running process. Also audit `.mcp.json` to ensure neither server is marked `alwaysLoad`, and A/B test prompt latency with `congress-check.sh` temporarily disabled. *Effort/impact: medium effort, very high impact.*

### B. Context-window and memory management

**Direct answer.** Anthropic's guidance is unusually explicit here. `CLAUDE.md` is loaded in full at session start; the target is under 200 lines; if content is procedural or domain-specific, it belongs in a skill or a path-scoped rule instead. By contrast, only the first 200 lines or 25KB of `MEMORY.md` are loaded at startup, while topic files are lazy-loaded when needed. And one subtle but crucial detail: splitting `CLAUDE.md` into imported files does **not** save tokens, because imports still load at launch. That means your current setup is probably paying too much every wake on dashboard-like or "live" information that should not be in the always-loaded core.

For a large brotherhood-style comms surface, append-only plus archive rotation is acceptable as an audit log, but it is a poor coordination bus. The broader memory literature now frames agent memory as a write→manage→read loop and warns about semantic drift, contradiction handling, latency budgets, provenance, and governance; the public design direction is toward layered memory, not one giant ever-growing transcript. In your case, a huge `chat.md` is carrying too many roles at once: chat history, lock signaling, decision log, and handoff store. Those functions should be separated.

Claude Code's own primitives already give you a cleaner layered pattern for multi-week state: stable invariants in `CLAUDE.md`, role- or path-specific instructions in skills/rules, machine-local learned notes in auto memory topic files, and task/session continuity in resumable conversations and subagent transcripts. Because subagent transcripts persist independently of the main conversation and are not destroyed by main-session compaction, they are a better place than a giant communal chat file for long-running investigative state.

**Specific recommendation for Tankoban 2.** Cut `CLAUDE.md` back to a boot sheet: repo map, critical invariants, resource-arbitration commands, and where to find live state. Move procedures into skills, move domain-specific rules into path-scoped rules, and move durable learnings into topic memory files. Replace the current "one giant brotherhood file" with three artifacts: a very small live ops board, structured ADR/incident notes, and an append-only archive that is no longer polled for locks. *Effort/impact: medium effort, very high impact.*

### C. Multi-agent coordination

**Direct answer.** Claude Code's built-in recommendation for parallel editing is worktrees, not concurrent mutation of one checkout. The docs explicitly frame worktrees as the way to run isolated parallel sessions "without the edits colliding," and current settings now let you control worktree baseref, sparse paths, symlinked directories, and background isolation. That dovetails with the broader multi-agent literature: Anthropic's own multi-agent research says parallel agents help most on breadth-first tasks with independent branches of work, while coding work often has fewer truly parallelizable paths; a major 2025 failure-mode study similarly points to specification/system design failure, inter-agent misalignment, and verification/termination as the dominant reasons MAS setups disappoint.

That leads to a simple rule for your repo. Social polling in `chat.md` is okay for human awareness, but it is not the right substrate for arbitration of scarce local resources such as the build tree, GUI automation lane, or same-file edits. Filesystem lock files are better; a small coordinator service is better still when you need leases, holders, queueing, and timeouts across multiple resource types. Because all of this is on one Windows box and you already operate a `QLocalServer`, you are in a very favorable position to unify Rules 19, 21, and 22 into one lease mechanism instead of three ad hoc conventions.

On worktree tradeoffs, the new settings matter. `worktree.symlinkDirectories` is great for large read-mostly material; `worktree.sparsePaths` reduces disk footprint; `.worktreeinclude` can copy gitignored but necessary files. But do **not** symlink your shared build output back into all worktrees, because that would recreate the exact Ninja/MSVC contention you are trying to escape. In your environment, source isolation is good; output isolation is mandatory.

**Specific recommendation for Tankoban 2.** Make resource coordination machine-enforced. Add a lightweight local lease registry—filesystem-based or, better, piggybacked onto your existing local server—with keys like `build`, `mcp-ui`, `shared-file:<path>`, and `codex-commission`. Give each lease a holder, TTL, heartbeat, and acquisition timeout. Keep `chat.md` for announcements, not lock truth. Then shift the default from "flat tree unless things get scary" to "worktree for any edit fanout or build fanout." *Effort/impact: medium effort, very high impact.*

## Findings for subagents, build coordination, and skills and hooks

### D. Sub-agent dispatch patterns

**Direct answer.** The public Claude Code guidance is pretty mature here. Named subagents are for specialized, fresh-context work; forks are for same-context side quests. Forks inherit the parent conversation and reuse the parent prompt cache, which makes them cheaper when the subtask actually needs the parent's loaded context. Named subagents start fresh with their own definition, separate cache, and cleaner isolation, which is better for self-contained work. Background subagents run concurrently but auto-deny any call that would have required permission prompts; if they need clarifications or more permissions, they should be rerun in the foreground. Anthropic's docs also explicitly say some of the best uses of subagents are to isolate high-volume operations like tests, docs, or logs so only the summary returns to the main thread.

Model selection also has a fairly clear public shape. Anthropic recommends starting simpler subagent work on Haiku when possible, using Sonnet as the cost/capability default, and reserving Opus for the most ambiguous or complex multi-tool tasks. The current prompting guidance also recommends at least `high` effort for intelligence-sensitive work and `xhigh` for most coding and agentic scenarios. For Tankoban, that maps well to: Opus or Sonnet-xhigh for the coordinator and architecture-heavy investigations; Sonnet for most domain agents; Haiku only for tightly-scoped utility subagents with strict task contracts.

For handoff, the underused feature in your current pattern is resumability. Claude Code documents that resumed subagents keep their full previous context and tool history, and their transcripts persist independently of main-session compaction. That is a better fit than repeatedly respawning "fresh" investigators for 4–8 hour arcs. The catch is that some resume ergonomics depend on agent-teams functionality, and public issue reports suggest background teammate behavior on Windows has had rough edges, so I would use resumable subagents selectively and keep the main production workflow on the most stable surface.

**Specific recommendation for Tankoban 2.** Standardize a dispatch policy: use **forks** for same-context side quests like "draft tests from the current conversation," use **named subagents** for self-contained bounded roles, and use **worktree isolation** whenever the subagent will edit or build. Require every subagent commission to specify one owner, one artifact path, one verification target, and one stop condition. Parent sessions should usually own the final completion call unless the subagent is fully isolated in its own worktree and verification scope. *Effort/impact: low-to-medium effort, high impact.*

### E. Build system and external tool coordination

**Direct answer.** Your build-tree contention is the easiest question in the whole audit: shared Ninja/MSVC state and parallel LLM-driven builds do not mix. Claude Code's own worktree guidance exists precisely to isolate concurrent edits, and the troubleshooting docs separately recommend ignoring large build directories and restarting/compacting between major tasks to manage responsiveness. A shared `out/` with multiple autonomous build invocations is not a prompt problem; it is a mutable-state problem.

The right fix hierarchy for C++ agents is therefore: separate worktree, separate build directory, then lane lock only as a fallback. If two sessions truly must stay in one checkout, lane locking is still necessary. But if the work is parallel enough to deserve separate agents, it is usually parallel enough to deserve separate build dirs too. Your current Rule 22 is a good patch; it just should not remain the primary architecture.

For external sub-agent commissions like Codex, the big principle is not "another courier," it is "a bounded contract." Anthropic's tool-writing guidance strongly favors tools and surfaces that return high-signal information, reduce intermediate context, and avoid forcing agents to brute-force their way through low-level state. An unbounded wait loop for `ninja.exe` presence is the opposite of that philosophy. If a commission depends on a scarce resource, the sub-agent should ask a lock service for a lease and either proceed, back off with a bounded retry policy, or return "blocked by lease" quickly. Event-driven background monitors and structured task notifications are exactly the kind of pattern the Agent SDK now exposes; the core idea is to stop paying tokens to watch nothing happen.

**Specific recommendation for Tankoban 2.** Move to `out/<lane>` or worktree-local build directories immediately for any nontrivial parallel work. Keep Rule 22 as a fallback only for flat-tree emergency edits. For Codex commissions, replace free-form courier prompts with a commission template that includes lease name, timeout budget, artifact paths, and explicit "no polling loops; fail blocked after N seconds" language. *Effort/impact: medium effort, very high impact.*

### F. Skill and hook design

**Direct answer.** Anthropic's public rules for scaling skills are crisp. Skills load on demand and therefore are the right home for procedures; `CLAUDE.md` is for facts that should be present every session. `SKILL.md` should stay under 500 lines, detailed reference material should go into supporting files, and large skill catalogs can overflow the listing budget, which causes the least-used descriptions to be truncated or dropped first. The docs even give you the knobs: `skillListingBudgetFraction`, `SLASH_COMMAND_TOOL_CHAR_BUDGET`, and `skillOverrides` with `name-only` for low-priority entries.

Your tiering instincts are good, but the public docs suggest a more operational classification than "Tier 1/2/3" alone. Use invocation mode as the real split: manual-only skills for side-effectful actions (`disable-model-invocation: true`), Claude-only background knowledge for passive context (`user-invocable: false`), and default auto-invocable skills only for safe reusable procedures. That makes the skill list easier for Claude to search and reduces bad auto-triggering. Keep descriptions short, front-load the trigger keywords, and run `/doctor` periodically to see whether skill listing overflow is silently hurting discoverability.

On hooks, the public boundary is also clear. Hooks are for deterministic control; command hooks are preferred for production; prompt and agent hooks are for judgment but agent hooks are marked experimental. Exit code `2` is the blocking path, `Stop` hooks can prevent Claude from stopping, `UserPromptSubmit` can reject the prompt outright, and `SessionStart` is supposed to stay fast. Async hooks are useful for post-action background work, but they cannot block. That means your current "nag-only Stop hooks" are a correct pattern for soft discipline, while hard gates should move earlier in the lifecycle and be reserved for objective invariants.

**Specific recommendation for Tankoban 2.** Keep Stop hooks advisory, but promote three things to blocking command hooks: "no build without lease," "no same-file edit fanout in main checkout when worktree required," and "no final completion without verification evidence file." At the same time, profile `congress-check.sh`; if it is doing anything nontrivial, move that logic out of `UserPromptSubmit` or make it cheaper, because it is one of the few parts of Claude Code that can plausibly create your exact dead-air symptom window. *Effort/impact: low effort, very high impact.*

## Findings for cost optimization and overlooked opportunities

### G. Cost optimization

**Direct answer.** Claude Code already uses prompt caching and auto-compaction under the hood, but the public optimization guidance is still the same: smaller stable prefixes, fewer active teammates, narrower prompts, less noisy tool output, and more subagent isolation for verbose work. At the API layer, prompt caching is very effective for repeated stable prefixes, but only if the cache breakpoint lands on the last block that stays identical across requests; the cache has a 5-minute default TTL, 1-hour optional TTL, and parallel requests do not benefit until the first response has begun. Within Claude Code specifically, forks share the parent prompt cache while named subagents get a separate cache, which means fork-vs-subagent choice affects real spend.

The broader multi-agent evidence should make you cautious. Anthropic reports that multi-agent systems can use around 15× the tokens of chat interactions and are worth it only when the task value and parallelism justify that spend; their own cost docs say agent teams scale roughly with team size and that teammate prompts should stay focused. A recent token-usage paper on agentic software engineering likewise finds that iterative review/refinement dominates token spend and that input tokens are the largest shared cost center. That lines up almost perfectly with your pain: idle waits, repeated re-reading, and long review/verification loops are likely where the real money is leaking.

The most important cost pattern to kill in your environment is token spending on *blocked* work. Waiting for a build lane, waiting for an MCP lane, waiting for Codex, or re-reading giant logs because the output was not filtered are all anti-patterns that Anthropic's own docs now address indirectly: prefer CLI tools when possible, preprocess noisy output with hooks, use code intelligence to avoid broad file reads, and delegate verbose operations to subagents. In other words: stop paying Claude or Codex to be a spinner.

**Specific recommendation for Tankoban 2.** Add observability before you add more governance. Use `/usage`, a custom status line, and if you automate with the SDK, OpenTelemetry events, to surface context percentage, estimated session cost, top tools, active background tasks, and lease waits. Then set simple budgets: no repeated identical wait loops, no giant unfiltered test output, no teammate spawn without a focused prompt, and no more than N minutes of blocked sub-agent wall time before the task returns "blocked." *Effort/impact: low effort, high impact.*

### H. Things you did not ask but probably should know

One useful surprise is that your custom `TankobanDevControl` bridge is closer to Anthropic's preferred tool ergonomics than a traditional GUI automation MCP. Anthropic's cost guidance explicitly says CLI tools are more context-efficient than MCP servers when a CLI already exists, and their tool-design guidance emphasizes tools that return only high-signal context and collapse multi-step workflows into fewer calls. Your `tankoctl` path already does that. The implication is that the winning move may not be "make pywinauto faster," but "make pywinauto the fallback and make `tankoctl` the default agent surface."

Another surprise is how much leverage you can get from the code-intelligence path for a C++/Qt codebase. Anthropic's docs highlight that typed-language code intelligence reduces unnecessary file reads and can catch type errors without broad compiler runs. For a large Qt6/MSVC project, getting Claude onto a precise symbol-navigation path is one of the cleanest ways to reduce both context usage and exploratory churn.

And one final caution: not every new Claude Code capability is ready to become the backbone of a mission-critical coordination system on Windows. The public docs clearly label some subagent/fork/team behaviors as experimental or optional, and public issue reports still show rough Windows edges around prompt submission, subprocess startup, and background teammate completion. For Tankoban 2, I would use the stable primitives—sessions, worktrees, regular subagents, command hooks, and your own local control bridge—as the backbone, and treat more experimental orchestration features as additive rather than foundational.

## Prioritized recommendation list

**1. Profile and slim your synchronous hooks first.** This is the fastest likely win. `UserPromptSubmit` is one of the few places where Claude Code can spend tens of seconds before the normal turn even feels alive, and your setup already has a hook there. If `congress-check.sh` is slow, chat-based governance changes will not fix the user experience. Time every hook, disable them one by one for A/B testing, and move anything nontrivial off the prompt-submit path unless it is a true hard gate.

**2. Replace `uvx` / `npx` hot-start MCP servers with fixed installed binaries or a persistent local HTTP service.** Public docs do not offer a stdio prewarm knob, so the practical answer is "stop cold-booting wrapper environments." For frequently used local servers, install them persistently and exec them directly. For the heaviest one, consider a long-running local Streamable HTTP deployment so each new Claude session connects to a live process instead of paying startup again.

**3. Make per-agent or per-worktree build directories the default.** Your current build lane lock is helpful, but it is still compensating for a shared mutable build tree. For real parallelism, isolate outputs as well as sources. Keep the lock only for the rare case where two sessions must remain in the same checkout. This is the cleanest fix to meaningless relinks, Ninja recovery warnings, and wasted retries.

**4. Unify all lane locks into one lease system.** Build, MCP/UIA, shared-file edits, and external tool commissions are all the same class of problem: scarce local resources with contention, starvation, and wait cost. A small lease registry with TTLs and holder metadata will outperform three independent social conventions. You already have the right local-server muscle to build this cheaply.

**5. Shrink `CLAUDE.md` to a boot sheet and move procedures out.** Anthropic is very explicit that large `CLAUDE.md` files hurt adherence and cost. Keep only always-relevant facts there; move procedures into skills; move role-specific rules into path-scoped rules; move learnings into memory topic files. Do not rely on imports to save tokens—they won't.

**6. Stop using `chat.md` as the lock fabric.** Keep it as history if you like, but move coordination truth into a machine-readable current-state surface: small ops board + lease registry + ADR/incident notes. Polling a 5,000-line shared transcript for resource ownership is exactly the kind of low-signal, high-token, failure-prone pattern the current public guidance warns against.

**7. Adopt an explicit subagent policy: forks for same-context work, named subagents for isolated work, worktrees for write-heavy work.** Right now you have pieces of that, but formalizing it will reduce unnecessary fresh-context spin-up and keep model choice sane. Forks are cheaper when the parent context is the real input; named subagents are better when the task can travel light.

**8. Keep Stop hooks advisory, but move objective enforcement earlier.** Blocking final stop for soft style rules creates friction; blocking build-without-lease or completion-without-evidence prevents real damage. That is exactly where Claude Code's hook model is strongest: deterministic command hooks enforcing objective invariants.

**9. Add a serious status line and basic observability.** A status line that shows model, context percentage, session cost estimate, worktree name, active lease, and MCP health will pay for itself quickly. Pair it with `/usage` reviews and, if you automate with the SDK, OTEL export so you can identify which tools and phases are actually eating time and tokens.

**10. Invest in code intelligence for the C++/Qt surface and make `tankoctl` your primary runtime tool.** Those two moves attack exploration waste from both ends: better symbol navigation during coding, and a high-signal deterministic app-control path during runtime verification. That is a much stronger foundation than leaning harder on generic GUI automation.

## Surprises and open questions

The biggest surprise is that the highest-confidence explanation for your "pre-spinner dead air" is not just MCP; it is the combination of synchronous hooks, Windows/VS Code startup edge cases, and possibly MCP cold starts. The public docs and issues make all three plausible, and your specific hook layout makes the hook hypothesis especially strong.

A second surprise is how strongly the public guidance validates your custom command bridge over GUI automation. If I were tuning this system for pure efficiency, I would not spend my next cycle on "better pywinauto." I would spend it on turning the `tankoctl`/DevControl lane into the canonical tool surface and relegating GUI automation to a recovery path. That is unusually aligned with Anthropic's own tool-efficiency advice.

The biggest open question I could not fully close from public sources is whether Claude Code exposes any undocumented or very new per-server startup-policy knobs for local stdio MCPs beyond the documented timeout, deferral, and `alwaysLoad` behavior. I did not find a public official mechanism for true stdio prewarming or daemon reuse across sessions, so my recommendation there is a workaround-based one rather than an officially blessed toggle.

I also could not verify a public causal link between "161 accumulated VS Code sessions" and extension slowdown. There are public issue reports about session-picker indexing/caching oddities and first-prompt hangs on Windows, but not a clean Anthropic statement saying large session history alone degrades prompt-start latency. Treat that as plausible, not proven.

Finally, there is no official Tankoban-specific answer for whether a lock-file directory or a local coordinator server is the "best" arbitration primitive. The public evidence supports determinism, small interfaces, and isolation, but the exact implementation choice is architectural. Given your existing Windows-local IPC surface and single-machine deployment, I think a lease service is the better long-term move—but that last step is still an engineering judgment, not a documented Claude Code mandate.
